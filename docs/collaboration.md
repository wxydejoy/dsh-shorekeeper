# 协作规则 · Shorekeeper

> 本仓库由「漂泊者」（人）+ 值班 agent 协作开发。规则优先级：本文档 > 各任务文档 > 个人习惯。改规则先改这份文档再动代码。

## 1. 角色与权限

| 角色 | 职责 | 边界 |
|---|---|---|
| 漂泊者（人） | 拍板方向、提供凭据（米家/token/key）、里程碑验收 | 唯一有权批准对外发布、删库、改本规则 |
| 值班 agent | 领任务、写码、自验、写验收记录 | 只在自己任务分支提交；不碰 main；不碰他人插件目录 |
| 审阅 agent（可选） | 交叉复核验收记录 | 只读 + 意见 |

## 2. 分支与提交

- `main` 受保护：只接受任务分支合并，合并前验收必须通过
- 任务分支命名 `T{编号}-{slug}`（如 `T2-k20-display`），一个任务一个分支，完成后合回 main 并删分支
- 提交信息用约定式前缀 + 中文描述：`feat: / fix: / docs: / refactor: / test: / chore:`，一次提交只做一件事
- 禁止 force push 到 main；任务分支 rebase 自便

## 3. 任务生命周期

每个任务文档（docs/tasks/）头部维护状态字段：

```
状态: todo → doing → review → done
owner: （领取人）· 开始于: 日期
```

1. **领取**：把状态改 doing、填 owner，开任务分支
2. **执行**：按任务文档步骤勾选 checkbox，遇到方案变更先改任务文档再改码
3. **自验**：验收标准逐条过，写验收记录到任务文档末尾（含证据：命令输出/截图路径）
4. **复核**：漂泊者或审阅 agent 过目 → 合并 → 状态 done
5. **卡住**：连续 3 次尝试失败就停下写清楚阻塞，换路或上报，不许蛮干

## 4. 并行协作

- 可并行的组合：`T2 ‖ (T3+T4) ‖ T5 ‖ T6`（T1 完成后）
- 互不碰的原则：每个 agent 只写自己的 `plugins/<自己的>/` 或 `content/`；共享区（`profile/`、根 README、本文件）改动必须在任务报告里声明
- 合并顺序按任务编号；冲突时后合并者负责解

## 5. 红线（违反即回滚）

1. `reference/` 只读——那是岸亭源码快照，改写对照用，不直接改
2. 凭据（token/api_key/米家账号）只进本机配置，永不进仓库和文档
3. 高危工具（熄屏、微信代发、米家写入）必须走审批 + 默认关闭，上线前逐个人工确认
4. 改协议先改文档（岸亭规矩）：涉及 LAN 协议的改动，先改 `reference/lan-protocol.md` 旁的变更记录，再动代码
5. 真机测试前先过 mock/演示模式（mihome 有演示模式，k20 有预览模式）

## 6. 代码规约

- TypeScript strict；每个插件一个目录，`package.json` 钉死 dsh 兼容版本范围
- 工具必须有 `parameters` / `output` schema，模糊匹配（如设备名）必须返回候选列表二次确认
- Config 声明 + Schemastery schema + 设置卡片三件套齐全才叫完工
- 每个插件自带 README（工具面、权限、验收）与单测；`npm test` 过才有资格提 review

## 7. 文档纪律

- 完工即更新：任务文档状态、refactor-map 的状态列、相关 README
- 决策留痕：方向性选择（如微信接入路线）写进任务文档的「决策记录」小节，不许口头定案
- 每个里程碑合并后打 tag（`M1`、`M2`、`v1.0`）
