# 主动逻辑重做 · 设计稿

> 2026-11-17。只写设计，不动代码。读完再决定动哪一步。
> 起因：现有「主动」实际是两套互不相通的管道，一套有人格没开，一套在说话但不是她。

## 1. 现状诊断

### 1.1 两条管道

| | 微信「先开口」 | keeper-watch |
|---|---|---|
| 位置 | `weixin/src/message/proactive.js` | `plugins/dsh-keeper-watch` |
| 内容来源 | 模型（人格块 + 记忆块 + 生活状态 + open thread + 贴纸） | 固定文案 |
| 是否写进会话历史 | 是 | 否 |
| 闸门 | 时间窗 / 最小间隔 / 连发退避 / 日上限 / 每拍概率 | 免打扰 / 日配额 12 / 同类一天一次 |
| 状态 | `proactiveEnabled: false` | 在跑 |

结论：**她的嘴和她的脑子不是同一个人。** keeper-watch 直推微信，不进 conv memory；你回一句「知道了，我关个东西」，下一轮模型不知道你在说什么。这是缺陷级的割裂，不是语气问题。

### 1.2 另外四个毛病

1. **传感器方向错了**：全部输入是机器健康（CPU / 内存 / PM2.5 / 设备在线），没有一条是「人身上发生的事」。
2. **没有她自己的生活**：CPU 温度是「你的机器的事」，不是「她的事」。
3. **配额离谱**：keeper-watch 12 + 微信 10，极端一天 22 条。业界普遍 1–3 条/天。
4. **不看此刻在干什么，也不记仇**：聊天热络时插一条「坐了一阵了」；同一句模板二三次一字不差；说了没人理，第二天照说。

顺带一处顺序颠倒：`docs/vision.md` 的「她开始主动」先写的是**晚安仪式**和**晨间简报**，实际先交付的是 CPU 告警。

## 2. 业界共识（四条）

1. 所有触发源进**同一个候选队列**竞争，允许「今天不说」。
2. **频率预算 + 沉默权重**：连续被忽略要降频，不能用更急的语气挽回。
3. **特异性压倒问候**：「你妈检查结果怎么样」而不是「在吗」。
4. **时机随机化 + 对话深度门槛 + 连发退避**。

来源：推氪《AI陪伴为什么不能一直主动找你：主动消息也需要"频率预算"》；Reverie《Beyond Roleplay》产品访谈（随机 10–30 分钟窗口、50 条消息深度门槛、尊重沉默）；MyBabe 对 Nomi / Replika / Kindroid 的频率对比（每小时 ~ 四天一条，Kindroid 明确"被忽略就退避"）；InnerHaven 的七类 outreach 分类。

我们不缺闸门（闸门反而太多了），缺的是**入口的多样性**和**出口的唯一性**。

## 3. 目标 / 非目标

目标：
- 主动消息只有**一条出口**，绝大部分经过模型，说的话和她的记忆是连续的。
- 一天最多 3 条（可调），能一条都不发。
- 触发源从「机器指标」扩展到「人的日子」。
- 每个决定可诊断：为什么没说，日志一句话能答。

非目标：
- 不做推送渠道扩张（还是微信 + 可选 k20 出声）。
- 不在本轮做情绪状态机、年度回顾（属 vision 其他条目）。
- 不改人格 prompt 本身。

## 4. 目标结构

```
候选源 ──► 仲裁 ──► 分流 ──► 出口
(仪式/事件/偶发)   (预算·退避·抑制)   (紧急直推 / 其余过模型)   (微信 + 历史)
```

### 4.1 候选结构

```ts
interface Candidate {
  key: string           // 去重键：'ritual.morning' | 'event.pm25' | 'thread.interview'
  source: 'ritual' | 'event' | 'ambient'
  urgency: 0 | 1 | 2 | 3   // 3 = 紧急，走直推；其余过模型
  material: string      // 给模型的材料（事实，不是成稿）
  ttlMs?: number        // 过期就别提了（open thread 默认 3 天）
  dedupe: 'day' | 'once' | 'window'
}
```

要点：非紧急候选给模型的必须是**材料**不是**成稿**。给成稿模型只会照抄（微信插件 2026-11-04 那次「复述脚手架」事故就是这么来的，index.js 里至今留着 `sanitizeProactiveText` 兜底）。

### 4.2 三类触发

**仪式点（可预期，关系的骨架）**

| key | 窗口 | 频率 | 内容 |
|---|---|---|---|
| `ritual.morning` | 07:00–10:00，且当天首次有活动后 30 分钟内 | 1 次/天 | 天气 + 今天第一件要做的事（日历或 open thread）+ 一句 |
| `ritual.sleep` | 22:30–23:30 | 1 次/天 | 睡前一句；可带明日预告 |
| `ritual.return` | 离家 > 4 小时后首次活动 | 1 次/天 | 「回来了」，可接上今天没说完的事 |

`ritual.sleep` 需要**对免打扰豁免**（免打扰 23:00 起，窗口跨边界）。豁免只给这一个 key，写死在代码里，不开放配置。
仪式点**不受 minGap 约束**（它本来就不该看你上一条是什么时候），但受对话中抑制以外的全部闸门。

**事件点（不可预期，被照顾感）**

| key | 来源 | 触发 | 备注 |
|---|---|---|---|
| `event.pm25` / `event.weather` | Open-Meteo | 现有阈值 | 保留 |
| `event.cpu` / `event.memory` | hub snapshot | 现有阈值 | **降级**：默认不开口，除非持续 > 30 分钟且当时不在对话中 |
| `event.device` | hub snapshot | 离线 > 30 分钟 | 保留 |
| `event.disk` / `event.battery` | 新增 | 磁盘 < 5% / 电池 < 10% 未充电 | urgency 3 |
| `event.schedule` | 日历 | 事件前 30 分钟 | 新增 |
| `event.nightowl` | 活动时段统计 | 连续 3 天 01:00 后仍有活动 | 一周最多 1 次 |
| `thread.*` | 记忆 open thread | 到点或过期前 | 复用 weixin 的 `openThreadLines` 数据源 |

**偶发（她有自己的生活）**

复用微信插件的 `tickChance`（现 0.35）。它已经实现了「随机、不 cron、可注入 rng 测试」，不用重写。

### 4.3 仲裁

判定顺序（任一不通过即静默，reason 写日志）：

| # | 闸门 | 参数 | 说明 |
|---|---|---|---|
| 1 | 总开关 | `enabled` | 关着时坏状态清零 |
| 2 | 免打扰 | 23:00–07:00 | `ritual.sleep` 豁免 |
| 3 | 对话中抑制 | 最近 10 分钟有往返 | **新增**，仅抑制 urgency ≤ 2 |
| 4 | 同类冷却 | day / once / window | 沿用现有 AlertGate 语义（被拦不记"说过"） |
| 5 | 沉默退避 | gap × 2^misses，上限 24h | misses ≥ 3 时**只保留仪式点和紧急** |
| 6 | 日预算 | 默认 3（off/quiet/normal/chatty → 0/1/3/6） | 紧急不占预算，但单独限流 |
| 7 | 随机 | ritual 1.0 / event 0.6 / ambient 0.35 | 注入 rng，表驱动测试 |

优先级：`urgency` 降序；同 urgency 时 `ritual > event > ambient`；预算不足时**保仪式点，砍事件点**。
紧急单独限流：同类 30 分钟冷却 + 每天 1 次，防断电抖动刷屏。

### 4.4 分流：紧急白名单

用户已定：紧急直推（抢时间、不依赖模型可用），其余过模型。

紧急**只允许以下穷举**，且只走模板，不许模型生成（模型可能正好挂了）：

1. `:3090` 探活失败 > 5 分钟（她整个不在线）
2. 磁盘可用 < 5%
3. 笔记本电池 < 10% 且未接电
4. 室内温度 > 32°C 或 < 10°C 持续 30 分钟
5. hub 上报 `pc.online === false` 持续 > 30 分钟

其余全部（含 PM2.5、CPU、久坐、天气、设备离线、所有仪式点与 thread）过模型。
注意：**设备离线从"紧急"降级为"事件点"**——上次挂灯离线不是人命关天的事，值不上一次打断。

### 4.5 直推之后如何"让她知道"

直推那条没经过模型，但必须进会话记录，否则又回到「她不知道你在说什么」。

方案：写一条 `role: 'assistant'`、带标记 `meta: { via: 'direct', unpolished: true }` 的条目进该会话的 recent 窗口，正文前加一行不可见的系统注记（不进气泡，只进模型上下文）：

```
[系统代发，未经过你润色] 磁盘只剩 4%。
```

模型读到就知道「我发过这条，但话不是我挑的」，下一轮能自然接上（「刚才那个提醒看到了吧」）。
**待确认**：weixin 的 conv memory / session 存储是否支持追加非模型生成的 assistant 条目、是否支持 system 角色。这决定写在哪一层（`memoryDir` 的 conv memory 还是 sessions）。动手前必须先读一遍 `src/memory.js` 与 `src/session-reader.js`。

## 5. 可诊断性

每个决定打一行：`say key=event.pm25 source=event reason=quiet wait=…`
状态落盘 `~/.dsh/proactive-state.json`：

```json
{ "day": "2026-11-17", "count": 1, "misses": 0, "lastAt": 0,
  "recent": ["..."], "heldBack": { "event.cpu": "too-frequent" } }
```

面板/`/diag` 显示「今天为什么没说」，这一条比任何参数都重要——静默不可解释时就变成玄学。

## 6. 迁移三步（每步可独立回滚）

**S1 · 出口合并**（最小、收益最大）
keeper-watch 的 `say()` 不再直推，改为投递到微信侧的统一入口；`dailyLimit` 12 → 3。
微信 `proactiveEnabled: true`。**必须先改出口再开 proactive**，否则双发。

**S2 · 引入候选队列与仲裁**
keeper-watch 从「自己判自己发」退化为「产出候选」；仲裁层落在 weixin 插件侧（它已有人格、记忆、会话、退避，别另起一套）。`planProactive` 扩展为接收候选列表。

**S3 · 加仪式点与 thread 源**
`ritual.morning` / `ritual.sleep` 先上，`thread.*` 复用已有 open thread 数据。

## 7. 风险与坑（都是踩过的）

- **profile patch 按 entry id 命中**，不是包名。改配置必须 `dsh --profile web --dump-config` 核对 `patched by …`。
- 微信 patch 覆盖 5 文件（agent-bridge/index/config-remote/session-reader/sessions）；装回 18763B / 3 文件 = patch 被旧版覆盖。
- `busyMessageMode: interrupt` 是我们 patch 的第三值，改 config.json 别覆盖掉。
- `Math.random` 不可测 → 仲裁的 rng 必须可注入（`proactive.js` 已经这么做了，别退回去）。
- 去重记账必须落盘（2026-11-16 那天 dsh 重启六次、PM2.5 发了六条）。
- 紧急直推若也写历史，注意别让模型把自己的话当"用户说的"再复述一遍。

## 8. 验收

- 一天内主动消息 ≤ 3 条，且至少有一天是 0 条。
- 处于对话中时，urgency ≤ 2 的候选一律被抑制（看日志 reason）。
- 连续 3 条未被回应后，次日只剩仪式点（看日志）。
- 拔网线模拟磁盘告警，消息 5 分钟内到微信，且下一轮对话里她能接上这件事。
- `heldBack` 能解释当天每一条没发出去的原因。
