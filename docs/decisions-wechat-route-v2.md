## 0. 一句话结论

**合规路线里不存在「读个人微信收件箱」这种接口。** 所以 T6 的目标从「她知道你微信里发生了什么」改成「在微信这一侧也能跟她说上话」——

- **入口（能收能发）**：企业微信 · 智能机器人（官方 API 模式 + WebSocket 长连接），首选插件 `dsh-wecom-bot@1.1.0`；
- **出口（只发不收）**：企业微信群机器人 Webhook，可选，用 `dsh-wechat-notice` 的企微通道；
- **个人微信（扫码登录、长轮询）**：技术上有一堆插件能做，但那是第三方网关的个人号自动化，不是官方对外的合规接口，**默认不采用**，仅作「只发通知」时的人工可选项记录在案。

原方案里的「代读 / 审批代发 / 发送白名单 / 封号风险签字」整块**作废**——目标变了，那些风险的载体不存在了。

## 1. 先把合规边界钉死

「合规」在这里只有一个意思：**走腾讯对外发布的官方接口**，不逆向、不 hook、不扫码登录个人号。

| 通道 | 官方接口 | 能收 | 能发 | 个人能不能弄 | 结论 |
|---|---|---|---|---|---|
| 个人微信（好友 / 群） | **无对外接口** | — | — | — | 合规路线下不可能，需求本身要改 |
| 企业微信 · 智能机器人 | `@wecom/aibot-node-sdk`，API 模式 + 长连接 | ✅ | ✅ | 需企业微信管理员在后台创建 | **主选** |
| 企业微信 · 群机器人 | 群 Webhook | ❌ | ✅（text / markdown） | ✅ 建群即得 | 仅作通知出口 |
| 企业微信 · 自建应用 | 官方应用 API | ✅（需可信 IP / 回调） | ✅ | 需管理员 | 备选，比机器人麻烦 |
| 公众号 · 客服消息 | 客服消息接口 | ✅ | ✅ | 仅服务号（企业主体），且 48h 互动窗口 | 不采用 |
| 微信客服 | `kf.weixin.qq.com` API | ✅ | ✅ | 需认证企业主体 | 不采用 |
| iLink Bot 网关（扫码长轮询） | 第三方网关，非对外合规接口 | ✅ | ✅ | ✅ | **灰色，不采用** |

> 注：公众号 / 微信客服两条是按「订阅号无客服消息、服务号需企业主体」的既有口径判断，**未实测**；因为主选已经够用，不再花时间验证。

## 2. 候选插件（npm 实查，2026-11-03 15:0x）

筛选口径：① 通道必须是官方接口；② 依赖线必须能吃现在的 dsh **0.2.1-rc.5**（peer 要么没有、要么范围覆盖 0.2.x）；③ 最好是「入口通道」而不是「单发通知」。

| 包 | 版本 | 发布 | 依赖面 | 通道 | 合规 | 判 |
|---|---|---|---|---|---|---|
| **dsh-wecom-bot** | 1.1.0 | 2026-10-23 | **无 peerDependencies**；`@wecom/aibot-node-sdk@1.0.7`、`schemastery ~3.18.4` | 企微智能机器人 · 官方长连接 | ✅ | **首选** |
| dsh-wecom | 0.5.3 | 2026-09-28 | peer 里钉了 `@deepseek-ai/dsh-session-persistence: 0.1.0-rc.6 \|\| 0.1.7-rc.2`（精确版本，非范围） | 企微智能机器人 · 官方长连接 | ✅ | 备选，装前必炸 peer |
| @xmanrui/dsh-im | 5.9.1 | 2026-10-31 | **无 peerDependencies**；企微同样走 `@wecom/aibot-node-sdk@1.0.7` | 十种 IM 一套插件（企微 / 飞书 / 钉钉 / QQ / Slack / TG…） | 企微通道 ✅ | 备选（将来要多 IM 再上） |
| dsh-wechat-notice | 0.9.0 | 2026-10-23 | peer 只有 `cordis ^4.0.1` | 企微信群机器人 Webhook（只发）＋ 个人微信 iLink（灰色） | 企微通道 ✅ | 只当通知出口时用，个人微信那条默认关 |
| dsh-wechat | 0.15.0 | 2026-11-02 | peer `@deepseek-ai/dsh >=0.2.1-0` | 个人微信 iLink 扫码 | ❌ 灰色 | 不采用，记录备查 |
| dsh-plugin-weixin | 1.4.3 | 2026-11-03 | peer `dsh-agent >=0.1.0-rc.6` | 个人微信 iLink 扫码 | ❌ 灰色 | 不采用 |
| dsh-wechat-plugin | 0.47.0 | 2026-10-26 | peer `dsh-home-paths >=0.1.7-rc.2 <0.3.0-0` | 个人微信 iLink 扫码 | ❌ 灰色 | 不采用 |

三个「个人微信」插件的能力其实都挺强（图文语音双向、白名单、会话切换、`/stop`），但**它们的合规性判断不取决于插件写得好不好，而取决于它接的那个网关是不是腾讯对外许可的接口**——这一点没有任何官方文档支持，所以不进主选。

### 为什么首选 dsh-wecom-bot 而不是 dsh-wecom

1. **依赖面干净**：无 peerDependencies，不会像 dsh-wecom 那样拿 `0.1.0-rc.6 || 0.1.7-rc.2` 的精确 peer 去撞 0.2.1-rc.5（[D3] 的教训：peer / linker 一打架，整行插件被 disable）。
2. **权限模型完整**：分组决定工作区 / 模型 / Agent 预设 / 工作区权限，默认「仅可查看」；管理员可远程审批工具调用。这条正好接得住 T3 的守岸人预设，也不会让远程聊天绕过审批。
3. **待授权机制**：陌生人只收到「用户未授权，请联系管理员」，不会直接驱动 agent。
4. 版本线比 dsh-wecom 新（1.1.0 / 10-23 vs 0.5.3 / 09-28），且依赖的是同一个官方 SDK 的更新版（1.0.7）。

## 3. 推荐架构（T6 改口径）

```
手机企微 ──私聊/群 @──▶ 企微智能机器人（官方长连接）
                              │  dsh-wecom-bot
                              ▼
                     dsh（shorekeeper profile）
                     ├─ Agent 预设：T3 的守岸人卡（人格/世界书）
                     ├─ 工具：desk-mi（米家/时钟）、k20（屏）、reading、weather…
                     └─ 会话：一人一会话，重启可续（sessionPersistence）
```

三条边界：

- **入口只有企微侧**，不碰个人微信；
- **群聊默认只允许 @ 触发**，且群和私聊可以分别 `open / allowlist / disabled`；
- **远程权限默认「仅可查看」**，要写文件、跑命令得管理员在手机上点审批——这条不许放宽成默认。

## 4. T6 任务书要改成什么

原任务书（`docs/tasks/T6-wechat.md`）整篇是按「读个人微信 + 摘要 + 代读 + 审批代发」写的，需按下面重写：

| 原内容 | 新口径 |
|---|---|
| 目标：她知道微信里发生了什么 | 目标：微信侧可作为第二入口跟守岸人对话 |
| 新消息摘要进上下文 | 删（拿不到个人微信，也没有摘要对象） |
| 按需代读 / 审批代发 | 删（→ 由入口会话内的正常对话替代） |
| 默认只读不发、发送白名单 | 删（→ 改为「默认仅可查看 + 工具审批」） |
| 三路线对比 + 风险签字区 | 删（→ 本文 §2 的合规对比） |
| Windows 挂机部署手册 | 删（→ 改为「企微机器人创建与接入手册」） |

新的阶段划分（**只列，不做**）：

1. **装前体检（0.5h）**：`shorekeeper-lab` 里 `dsh plugin add dsh-wecom-bot@1.1.0` → 看 boot log 有没有 disable / import 报错 → 无凭据时插件应优雅待配置而不是崩。**体检不过就退回 `@xmanrui/dsh-im` 或 `dsh-wecom`，不硬啃。**
2. **建机器人（人工，漂泊者）**：企业微信管理后台 → 智能机器人 → API 模式 → 拿 Bot ID / Secret。**这一步 agent 做不了**（需要主体账号）。
3. **接线（1–2h）**：Secret 进凭据库（`WECOM_BOT_SECRET`，参照 [D8] 的 refs 机制，**不进仓库不进文档**）；管理员加入；把 T3 的守岸人预设绑成默认预设。
4. **剧本验收**：私聊 `/help` → 一句人话 → 她按守岸人口吻答；`/stop` 能打断；未授权账号被拒；重启 dsh 后会话还在。
5. **文档回灌**：踩坑写回 `profile/README.md`；接入步骤单独成一篇手册。

验收线（替代原来的「微信摘要」验收）：

## 6. 定案（漂泊者 2026-11-03 15:10：按最优定，不再逐条问）

四条待决全部按「能力最全 + 风险最低 + 迁移成本最小」拍了：

| 原待决 | 定 |
|---|---|
| 通道选谁 | **`dsh-wecom-bot@1.1.0`**（企微智能机器人 · 官方长连接）。理由是本文 §2 那四条：无 peer 冲突、官方 SDK、权限模型完整、待授权机制齐。`dsh-wecom` 只在体检不过时顶上来 |
| 私聊还是群 | **私聊是主入口**；**群通道同时开，但默认 `allowlist`**——只放行指定的群，群里必须 @ 才应答。理由：群 @ 有用（出门在外同事/家人也能找她），但默认开等于把噪音源引进家里 |
| 要不要通知出口 | **要，一起装** `dsh-wechat-notice@0.9.0`，**只启企微群机器人通道，个人微信通道关闭**。理由：agent 跑完、要审批、报错这三种事件只有推到手机才有用；企微 webhook 零登录零风险，与入口互补 |
| 要不要一步到 `dsh-im` | **不上。** 一条通道先跑通。将来真要飞书/钉钉/QQ，再换 `@xmanrui/dsh-im`（企微走同一个官方 SDK，迁移面小），但那是 M3 之后的事 |

**唯一的现实前提**（不是待答，是待验证）：需要一个能建「智能机器人（API 模式）」的企业微信主体。没有就走降级路径——入口退到桌面/手机浏览器 + 通知出口用群 webhook，其余不变。这条写进 §7 风险表第一行。

## 7. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| 企业微信门槛 | 智能机器人可能需要认证主体 / 管理员权限 | 先确认主体；不行退「自建应用」或只做通知出口 |
| 依赖线漂移 | 0.2.1-rc.5 与插件写的 0.1.x API 有差 | 装前体检；不过就换 dsh-im / dsh-wecom，再不行自写薄桥 |
| 双入口打架 | k20 屏与企微同时在线，谁是主入口 | 默认「屏是脸，企微是备用入口」；两边都走同一个 profile 的不同会话，不共享上下文 |
| 群聊噪音 | 群里 @ 就唤醒，容易被同事逗 | 群通道默认 `allowlist` 或 `disabled`，只放自己要用的群 |
| 远程权限过宽 | 手机端能审批，等于把 shell 递出去 | 分组默认「仅可查看」；高危工具保持默认关 |
